# LumoStage 발표 대본

**발표 시간:** 10분 (발표 5분 + 시연 5분)
**발표자:** 김재준 (디지털미디어학과)
**날짜:** 2025-11-30

---

## 발표 대본 (5분)

### 슬라이드 1: 타이틀

안녕하세요. 디지털미디어학과 김재준입니다.

오늘 제가 발표할 프로젝트는 LumoStage, 웹 기반 실시간 3D 조명 시뮬레이션 플랫폼입니다.

---

### 슬라이드 2: 프로젝트 개요

LumoStage는 영상 제작 현장의 실질적인 문제를 해결하기 위해 만들어졌습니다.

먼저 현재의 문제점을 살펴보면, 실제 촬영 현장에서 조명을 설치하고 테스트하는 데 엄청난 시간과 비용이 듭니다. Cinema 4D나 Blender 같은 전문 3D 소프트웨어는 고가이면서도 배우기가 너무 어렵습니다. 그리고 팀원들끼리 조명 구도를 말로 설명하기가 정말 어렵죠.

LumoStage는 이런 문제를 어떻게 해결할까요?

첫째, 설치가 필요 없습니다. 웹 브라우저만 있으면 바로 사용할 수 있습니다.
둘째, 조명과 카메라 구도를 실시간으로 시뮬레이션할 수 있습니다.
셋째, 초보자부터 전문가까지 누구나 쉽게 사용할 수 있도록 설계했습니다.

주요 타겟 사용자는 영화나 영상을 전공하는 학생들, 독립 영화 제작자, 그리고 영상 크리에이터입니다.

---

### 슬라이드 3: 기술 스택

LumoStage는 최신 웹 기술을 활용해서 만들었습니다.

프론트엔드는 React 18과 Vite로 빠른 개발 환경을 구축했고, 앱 전체에서 데이터를 공유하는 전역 상태 저장소로 Zustand를 사용했습니다.

3D 렌더링은 Three.js를 React와 통합한 React-Three-Fiber로 구현했습니다. 이를 통해 웹 브라우저에서도 실시간 3D 그래픽을 부드럽게 렌더링할 수 있습니다.

UI는 Tailwind CSS와 shadcn/ui 디자인 시스템을 활용해서 깔끔하고 일관성 있게 만들었습니다.

백엔드는 Node.js와 Express로 서버를 구축했고, 코드를 역할별로 분리해서 관리하는 MVCS 패턴을 적용했습니다. 데이터베이스는 MongoDB를 사용하고, 대용량 3D 파일이나 배경 이미지는 Cloudflare R2 클라우드 스토리지에 저장합니다.

인증은 Session 방식으로 안전하게 구현했고, 구글과 네이버 소셜 로그인도 지원합니다.

그리고 최근에 구현한 AI 통합 기능에서는 Google의 Gemini 2.5 Flash 모델을 사용해서 3D 장면을 실제 사진처럼 변환할 수 있습니다. 비동기 작업 처리를 위해 Bull Queue를 사용하고, 사용자의 API 키는 AES-256-GCM 암호화로 안전하게 보호합니다.

---

### 슬라이드 4: 시스템 아키텍처

시스템의 데이터 흐름을 간단히 설명드리겠습니다.

사용자가 UI에서 조명을 조정하거나 마네킹 포즈를 변경하면, 이 변경사항이 Zustand 전역 저장소로 전달됩니다. 전역 저장소가 업데이트되면 자동으로 화면이 다시 그려지면서 3D Scene에 즉시 반영됩니다.

그리고 이 변경사항을 서버에 저장할 때는 API를 통해 Express 서버로 전달되고, 서버는 데이터를 검증하고 정리한 뒤 MongoDB에 저장합니다. 저장이 완료되면 정리된 데이터를 다시 클라이언트로 보내서 상태를 동기화합니다.

이렇게 단방향으로 데이터가 흐르기 때문에 예측 가능하고 디버깅하기 쉬운 구조입니다.

---

### 슬라이드 5: 데이터베이스 ERD

데이터베이스는 크게 세 가지 모델로 구성됩니다.

User 모델은 사용자 정보를 저장합니다. 이메일, 비밀번호, 구글이나 네이버 소셜 로그인 ID 등이 포함됩니다.

Project 모델은 사용자가 만든 3D 장면 프로젝트를 저장합니다. 프로젝트 이름, 설명, 썸네일, 그리고 실제 3D 장면 데이터가 JSON 형태로 저장됩니다. 각 프로젝트는 만든 사람인 owner와 연결되어 있습니다.

Asset 모델은 사용자가 업로드한 3D 모델 파일이나 배경 이미지를 관리합니다. 파일이 Cloudflare R2에 저장되면 그 위치와 메타데이터를 여기에 기록합니다. 프로젝트가 삭제되면 관련 파일들도 자동으로 삭제되도록 Cascade 삭제 로직을 구현했습니다.

---

### 슬라이드 6: API 구조

API는 크게 인증 API와 프로젝트 API로 나뉩니다.

인증 API는 회원가입, 로그인, 구글/네이버 소셜 로그인을 처리합니다. 로그인하면 세션이 생성되고, 이후 모든 요청에서 이 세션으로 사용자를 식별합니다.

프로젝트 API는 프로젝트 목록 조회, 새 프로젝트 생성, 프로젝트 불러오기, 수정, 삭제 기능을 제공합니다. 모든 프로젝트 API는 로그인한 사용자만 사용할 수 있도록 인증 미들웨어로 보호됩니다.

---

### 슬라이드 7: Scene Data 구조

3D 장면 데이터는 여러 요소로 구성됩니다.

조명 정보에는 Spot Light, Rect Area Light 등 다양한 조명의 위치, 색상, 밝기, 그림자 설정 등이 포함됩니다.

마네킹 정보에는 3D 인체 모델의 위치와 각 관절의 회전값이 저장됩니다. 팔이나 다리를 어떻게 움직였는지 모든 포즈가 기록됩니다.

카메라 정보에는 카메라의 위치, 보는 방향, 시야각 등이 저장됩니다.

배경 설정에는 HDRI 환경 이미지나 단색 배경 색상 정보가 들어갑니다.

이 모든 데이터는 JSON 형태로 MongoDB에 저장되고, 프로젝트를 불러올 때 정확히 같은 상태로 복원됩니다.

---

### 슬라이드 8: 주요 기능 (Phase 1-7 완료)

프로젝트는 7단계로 나눠서 개발했습니다.

Phase 1에서는 기본 3D 장면과 Zustand 상태 관리 구조를 만들었습니다. React와 Three.js를 연결하는 기반을 다졌죠.

Phase 2에서는 다양한 조명 타입과 Cinema 4D 스타일 카메라 컨트롤을 구현했고, 실수했을 때 되돌릴 수 있는 Undo/Redo 기능을 추가했습니다.

Phase 3에서는 백엔드 서버와 데이터베이스를 연결해서 프로젝트를 저장하고 불러올 수 있게 만들었습니다. 프로젝트 썸네일도 자동으로 생성됩니다.

Phase 4에서는 처음 사용하는 사람을 위한 8단계 튜토리얼을 만들었습니다. 단축키 안내도 제공해서 효율적으로 작업할 수 있습니다.

Phase 5에서는 사용자가 직접 3D 모델이나 HDRI 배경 이미지를 업로드할 수 있도록 Cloudflare R2 스토리지를 연동했습니다.

Phase 6에서는 전문가들을 위한 UI를 만들었습니다. Outliner로 장면의 모든 요소를 트리 구조로 보고, Inspector에서 세밀하게 조정할 수 있습니다.

Phase 7에서는 AI 프리비주얼라이제이션 기능을 추가했습니다. Gemini AI를 사용해서 3D 장면을 실제 사진처럼 변환할 수 있습니다. 이 작업은 시간이 걸리기 때문에 Queue 시스템으로 백그라운드에서 처리하고, 완료되면 알림으로 알려줍니다.

---

### 슬라이드 9: 핵심 코드 - Zustand 상태 관리

핵심 코드를 간단히 설명드리겠습니다.

Zustand는 앱 전체의 상태를 중앙에서 관리하는 저장소입니다. 여기에는 조명 목록, 마네킹 정보, 카메라 위치, 배경 설정 등 모든 3D 장면 데이터가 들어있습니다.

예를 들어 조명을 추가하는 addLight 함수를 보면, 조명 타입에 따라 기본 설정을 만들고 고유 ID를 부여한 뒤 조명 목록에 추가합니다.

조명을 삭제하는 removeLight는 ID로 조명을 찾아서 목록에서 제거하고, 히스토리에 저장해서 나중에 되돌릴 수 있게 합니다.

이렇게 모든 변경 작업은 Zustand 액션을 통해서만 이루어지고, 상태가 변경되면 자동으로 화면이 업데이트됩니다. 이게 바로 단방향 데이터 흐름의 핵심입니다.

---

### 슬라이드 10: 핵심 코드 - Backend MVCS 패턴

백엔드는 MVCS 패턴으로 구조화했습니다.

Controller는 HTTP 요청 검증과 응답 처리를, Service는 비즈니스 로직과 데이터 정규화를, Model은 MongoDB 스키마를 담당합니다.

특히 Scene 데이터 정규화가 중요했습니다. 프론트엔드에서 온 조명 데이터가 오염되거나 중복되는 문제가 있었는데, Service 레이어에서 normalizeSceneData 함수로 모든 데이터를 검증하고 정리해서 데이터베이스에 저장하도록 했습니다.

---

### 슬라이드 11: 어려웠던 점

개발하면서 정말 어려웠던 부분들을 공유하겠습니다.

첫 번째는 OrbitControls와 카메라 상태 동기화였습니다. Three.js의 OrbitControls는 자체적으로 카메라를 움직이는데, 이걸 사용자가 설정한 카메라 뷰로 정확히 맞추는 게 까다로웠습니다. Cinema 4D처럼 양방향 동기화를 구현해서 해결했습니다.

두 번째는 Zustand Store 관리였습니다. 처음엔 모든 기능을 한 파일에 넣다 보니 8000줄이 넘어가면서 관리가 불가능해졌습니다. Store를 분리하려고 했더니 순환 참조 문제가 발생했고, Immer 라이브러리를 도입했다가 성능 문제로 다시 되돌리기도 했습니다. 초기 설계가 얼마나 중요한지 뼈저리게 느꼈고, 테스트 코드가 없어서 리팩토링할 때마다 버그가 생기는 게 정말 힘들었습니다.

세 번째는 Scene 데이터 정규화 문제였습니다. 프로젝트를 저장하고 불러올 때 데이터가 오염되어서 조명이 중복되거나 이상한 값이 들어가는 버그가 많았습니다. normalizeSceneData 함수를 만들어서 모든 데이터를 검증하고 정리하도록 했고, 버전 관리 시스템도 추가해서 구버전 프로젝트도 안전하게 불러올 수 있게 했습니다.

네 번째는 대용량 파일 업로드였습니다. HDRI 파일은 최대 50MB, 3D 모델은 100MB까지 되는데 로컬 서버로는 감당이 안 됐습니다. Cloudflare R2 클라우드 스토리지로 전환하고, 프로젝트 삭제 시 관련 파일도 자동으로 삭제되도록 Cascade 삭제 로직을 구현했습니다.

---

### 슬라이드 12: 난이도 높은 구현 요소

기술적으로 난이도가 높았던 구현 요소들입니다.

실시간 3D 프리비주얼 뷰포트는 별 5개 난이도였습니다. React-Three-Fiber와 OrbitControls를 완벽히 동기화하고, HDRI 배경 이미지를 로드할 때 색상 매핑을 정확히 처리하고, Transform 모드와 Orbit 모드가 서로 충돌하지 않도록 잠금 로직을 구현하는 게 정말 복잡했습니다.

Undo/Redo 히스토리 시스템도 별 5개였습니다. 최대 50개의 상태 스냅샷을 메모리에 저장하면서도 성능을 유지해야 했고, 조명이나 카메라 같은 복잡한 객체를 깊은 복사해야 했습니다. 그리고 Transform이 끝나는 시점에만 히스토리에 저장해서 불필요한 중간 상태는 기록하지 않도록 최적화했습니다.

AI 프리비주얼라이제이션도 별 5개였습니다. 3D 장면을 Gemini AI가 이해할 수 있는 프롬프트로 변환하고, 비동기 작업을 Queue로 관리하고, 사용자의 API 키를 안전하게 암호화해서 저장하는 전체 파이프라인을 구축하는 게 도전이었습니다.

---

### 슬라이드 13: 개발 현황 및 향후 계획

현재 Phase 1부터 7까지 핵심 기능은 모두 구현 완료했습니다.

Phase 8에서는 기술 부채를 정리하고 성능을 최적화할 계획입니다. 특히 8000줄이 넘는 Zustand Store를 깔끔하게 분리하고, Immer를 다시 도입해서 코드 가독성을 높일 예정입니다.

또한 E2E 테스트를 도입해서 사용자 시나리오를 자동으로 테스트하고, 앞으로 새로운 기능을 추가할 때 기존 기능이 망가지지 않도록 보장할 계획입니다.

마지막으로 팀 협업 기능을 추가해서 URL 공유만으로 여러 사용자가 동시에 같은 프로젝트를 편집할 수 있도록 WebSocket 기반 실시간 동기화를 구현할 예정입니다.

### 시연 목표

사용자 여정을 따라가며 LumoStage의 핵심 기능을 5분 안에 효과적으로 보여주기

### 시연 체크리스트

#### 1단계: 프로젝트 대시보드 (30초)
- [ ] 홈페이지에서 "프로젝트" 버튼 클릭
- [ ] 프로젝트 목록 카드 UI 보여주기
- [ ] "새 프로젝트" 버튼으로 새 프로젝트 생성 시작

**강조 포인트:**
- 깔끔한 프로젝트 카드 디자인
- 썸네일 자동 생성
- 직관적인 레이아웃

#### 2단계: 에디터 진입 & 기본 UI (30초)
- [ ] 에디터 화면 로드
- [ ] 3D 뷰포트 (왼쪽), 에디터 패널 (오른쪽) 구조 설명
- [ ] 기본 마네킹과 조명 확인

**강조 포인트:**
- 실시간 3D 렌더링
- Cinema 4D 스타일 인터페이스
- 깔끔한 화면 분할

### 예상 질문 & 답변 준비 (교수님 질문 대비)

**Q1: Zustand를 선택한 이유는? Redux나 Context API와 비교했을 때 장단점은?**

A: Redux는 보일러플레이트가 너무 많고, Context API는 성능 문제가 있었습니다. Context는 값이 변경되면 모든 구독 컴포넌트가 리렌더링되는데, 3D Scene처럼 자주 업데이트되는 상태에는 치명적입니다.

Zustand는 가볍고(2KB), 선택적 구독이 가능해서 필요한 상태만 구독할 수 있습니다. 예를 들어 조명 목록만 필요한 컴포넌트는 `const lights = useStore(state => state.lights)`로 조명만 구독하기 때문에 카메라 상태가 변경되어도 리렌더링되지 않습니다.

단점은 TypeScript 타입 추론이 Redux Toolkit보다 약하고, 미들웨어 생태계가 작다는 점입니다. 하지만 이 프로젝트 규모에서는 Zustand의 단순함이 더 큰 장점이었습니다.

---

**Q2: Scene 데이터를 JSON으로 저장하는 방식의 트레이드오프는? 관계형 DB로 정규화하지 않은 이유는?**

A: 관계형 DB로 정규화하면 조명 테이블, 마네킹 테이블, 카메라 테이블을 따로 만들어야 하는데, 이렇게 하면 데이터를 불러올 때 JOIN이 복잡해지고 쿼리가 느려집니다.

3D 장면 데이터는 항상 전체를 한 번에 불러와서 한 번에 저장하는 패턴이기 때문에, MongoDB의 Document 기반 저장이 훨씬 효율적입니다. 하나의 쿼리로 전체 장면을 가져올 수 있고, 트랜잭션도 단순합니다.

단점은 데이터 중복과 일관성 문제인데, 이걸 해결하기 위해 Service 레이어에서 normalizeSceneData 함수로 모든 데이터를 검증하고 정리합니다. 조명 ID 중복 체크, 잘못된 타입 필터링, 기본값 설정 등을 수행해서 데이터 품질을 보장합니다.

---

**Q3: Session 방식을 선택한 이유는? JWT와 비교했을 때 장단점은?**

A: JWT는 stateless하고 확장성이 좋지만, 로그아웃 처리가 어렵고 토큰이 탈취되면 만료 전까지 무효화할 방법이 없습니다.

Session은 서버에서 즉시 무효화할 수 있어서 보안성이 높습니다. AI API 키처럼 민감한 정보를 다루는 프로젝트이기 때문에 세션을 선택했습니다. 또한 MongoDB Session Store를 사용해서 서버가 재시작해도 세션이 유지됩니다.

단점은 서버 메모리 사용량이 증가하고, 로드 밸런서 환경에서 sticky session이 필요하다는 점입니다. 하지만 현재는 단일 서버로 운영하고, 향후 확장 시에는 Redis Session Store로 전환할 계획입니다.

---

**Q4: Zustand Store가 8000줄이 넘어간 이유와, 이를 어떻게 리팩토링할 계획인가?**

A: 초기에는 모든 상태와 액션을 하나의 파일에 넣었습니다. lights, mannequins, camera, background, history 등 모든 도메인이 한 곳에 있다 보니 파일이 계속 커졌습니다.

분리를 시도했을 때 순환 참조 문제가 발생했습니다. 예를 들어 조명 Store에서 히스토리 Store의 액션을 호출하고, 히스토리 Store에서 조명 Store의 상태를 읽으려니 순환 참조가 생겼습니다.

해결 방법은 Zustand의 slice 패턴입니다. createLightsSlice, createCameraSlice처럼 각 도메인을 독립적인 slice로 만들고, 최종적으로 하나의 Store로 합칩니다. 순환 참조는 의존성 주입 패턴으로 해결할 예정입니다.

---

**Q5: Three.js 성능 최적화는 어떻게 했나요? 렌더링 프레임 드랍 문제는 없었나요?**

A: 가장 큰 문제는 상태가 변경될 때마다 전체 Scene이 리렌더링되는 것이었습니다.

React.memo로 컴포넌트를 메모이제이션했지만 props가 자주 변경되면 소용없었습니다. 그래서 Zustand의 선택적 구독을 활용했습니다. 조명 컴포넌트는 해당 조명의 상태만 구독하고, 다른 조명이 변경되어도 리렌더링되지 않도록 했습니다.

또한 Transform 중에는 히스토리에 저장하지 않고, Transform이 끝날 때만 저장해서 불필요한 상태 복사를 줄였습니다.

HDRI 이미지는 TextureLoader로 비동기 로드하고, 로드되기 전까지는 단색 배경을 보여줍니다. 일반 노트북에서도 60fps를 유지합니다.

**Q6: Bull Queue를 선택한 이유와, AI 비동기 작업 처리 아키텍처를 설명해주세요.**

A: Gemini AI 요청은 5~10초 정도 걸리기 때문에 HTTP 요청으로 처리하면 타임아웃이 발생합니다. 비동기 작업 Queue가 필요했습니다.

Bull은 Redis 기반의 성숙한 Queue 라이브러리입니다. Job 재시도, 우선순위, 동시성 제어 등을 지원합니다.

작동 방식은 이렇습니다:
1. 클라이언트가 `/api/ai/generate` POST 요청 → 즉시 Job ID 반환
2. Bull Worker가 백그라운드에서 Job 처리 (3D Scene 렌더 → Gemini API 호출 → R2 업로드)
3. 클라이언트는 `/api/ai/status/:jobId` GET으로 폴링
4. 완료되면 결과물 URL 반환

실패 시 자동 재시도(최대 3회)하고, 사용자별 Rate Limiting(시간당 10회)도 적용했습니다.

**Q7: MVCS 패턴에서 각 레이어의 책임을 어떻게 나눴나요? Service와 Controller의 경계는?**

A: 명확한 책임 분리가 중요했습니다.

**Controller**: HTTP 계층만 담당합니다. 요청 파싱, 입력 검증(express-validator), 인증 확인, HTTP 응답 전송. 비즈니스 로직은 절대 포함하지 않습니다.

**Service**: 순수한 비즈니스 로직입니다. normalizeSceneData, 중복 제거, 데이터 변환 등. Service는 HTTP를 모릅니다. req, res 객체를 받지 않습니다.

**Model**: Mongoose 스키마와 validation만 담당합니다. 복잡한 로직은 Service로 위임합니다.

예를 들어 프로젝트 업데이트 로직:
- Controller: req.body 검증, req.user로 권한 확인
- Service: sceneData 정규화, 버전 체크, thumbnail 생성
- Model: MongoDB 저장

이렇게 분리하면 Service를 CLI나 다른 컨텍스트에서도 재사용할 수 있습니다.

---

**Q8: 데이터 정규화 함수(normalizeSceneData)가 구체적으로 어떤 문제를 해결했나요?**

A: 프론트엔드에서 올라오는 데이터가 신뢰할 수 없었습니다. 조명 ID가 중복되거나, 삭제된 조명이 배열에 남아있거나, undefined 값이 섞여있었습니다.

normalizeSceneData는 다음을 수행합니다:
1. 조명 배열에서 null/undefined 필터링
2. 중복 ID 체크 및 재생성
3. 필수 필드(type, position, color 등) 기본값 설정
4. 지원하지 않는 조명 타입 제거
5. 숫자 범위 검증 (intensity는 0~10, color는 0~1 등)

이걸 하기 전에는 프로젝트를 불러올 때 조명이 2배로 복제되거나, 색상이 깨지는 버그가 많았습니다. 정규화 후에는 데이터 품질이 보장되어 버그가 거의 사라졌습니다.

---

**Q9: 단방향 데이터 흐름을 선택한 이유와, 양방향 바인딩과 비교했을 때 장단점은?**

A: 양방향 바인딩(Vue v-model 같은)은 편하지만 데이터 흐름을 추적하기 어렵습니다. 특히 3D Scene처럼 복잡한 상태에서는 어디서 상태가 변경되는지 알기 힘듭니다.

단방향 데이터 흐름은:
- UI 이벤트 → Zustand 액션 호출 → Store 업데이트 → Scene 리렌더링

이렇게 항상 한 방향으로만 흐르기 때문에 디버깅이 쉽습니다. Redux DevTools로 모든 상태 변경을 시간 순으로 볼 수 있습니다.

단점은 코드가 조금 더 길어진다는 것입니다. 슬라이더 값을 변경하려면 onChange 핸들러를 만들고, 액션을 호출해야 합니다. 양방향이면 v-model 하나로 끝나는데 말이죠.

하지만 유지보수성과 예측 가능성을 위해 단방향을 선택했고, 지금까지 만족하고 있습니다.
